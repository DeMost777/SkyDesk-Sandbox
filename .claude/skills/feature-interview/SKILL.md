# Skill: Feature Interview

Проверка готовности перед новой фичей или виджетом. Первый прогон — виджет Passengers (коммит `9b274e2`, `projects/booking-overview/passengers-widget.md`).

Цель: до кода знать, что источники уже говорят, что остаётся допущением, а что без ответа пользователя придётся переделывать. «Не выдумывать продукт» (`CLAUDE.md` → «Источники истины»): спрашиваем только то, чего источники не показывают.

Не нужен для правки существующего экрана или состояния — там хватает flow doc.

## 1. Запросить материалы

Одним сообщением, а не по одному. Сказать, что не всё обязательно: пользователь отвечает, что есть.

1. **Спецификация** — текст как есть, с повторами.
2. **Figma** — ссылка на файл и узел (file key и node id). Секция спецификации, если она есть: там бывают заметки авторов («Вопросы», аннотации разработчикам).
3. **Скриншоты и запись production Skydesk** — как это выглядит и ведёт себя сейчас.
4. **Данные** — какие поля у сущности, откуда берутся (GDS, Skydesk), какие значения возможны.
5. **Сценарии и edge cases** — пустое, много, длинное, частичное; что нельзя пропустить.
6. **Тексты** — подписи, пустые состояния, подсказки.
7. **Место и поведение** — где на странице, порядок, развёрнуто ли по умолчанию, что кликабельно.
8. **Что не входит в V1.**

Нет Figma — фича идёт по спецификации и скриншотам, это отмечается в карточке готовности.

## 2. Прочитать и сохранить

- **Спецификация** — в `projects/<flow>/sources/<name>-spec-v1.md` как прислана (шапка: источник, дата, Figma file key и секция). Выводы из неё — во flow doc, не в источнике.
- **Figma** — субагентом `figma-reader`; node id → `docs/figma-map.md` (раздел «не построен»), file key тоже. В источник — значения из узлов (размеры, токены, состояния) и дословно заметки авторов: их вопросы часто и есть open questions.
- **Скриншоты и запись** — в источник записать **структуру**: что на экране, какие состояния, что делает клик и Tab. Сами файлы в репозиторий не класть, если на них данные, похожие на реальные (имена, даты рождения, номера документов, PNR). Mock-данные только вымышленные. Реальных данных в репозитории нет.
- Источники расходятся (спецификация говорит `CNN`, production показывает `CHD`) — не выбирать молча: записать расхождение, решить по порядку из `CLAUDE.md`, остальное — вопрос.

## 3. Проверить готовность

Пройти по областям. Каждой — статус и откуда он:

| Область | Что проверить |
|---|---|
| Назначение | Какую задачу агента решает, что показывает, чего не делает |
| Данные | Поля, типы, формат значений, какие обязательны, откуда в Booking; есть ли в модели (`src/lib/booking.ts`) |
| Правила | Условия показа, индикаторы, статусы, что считается «введённым»; как формулируются в `src/lib/` |
| Состояния | Пусто, одно, много, длинное, частичное; loading / error; как открыть каждое (адрес, mock-сценарий) |
| Тексты | Подписи, пустые значения, подсказки; термины из глоссаря |
| Взаимодействие | Клик, hover, focus, клавиатура, раскрытие; что остаётся в DOM |
| Визуал | Figma-узлы, токены, размеры, типографика; чего нет в макете (Pressed, узкое окно) |
| Место | Где на странице, порядок, состояние по умолчанию, счётчик |
| Связи | Что общего с другими виджетами (`WidgetSection`, `RefBadge`, одни данные Booking); новые зависимости и токены |
| Вне V1 | Что осознанно не делаем |

Статус области:

- **Есть** — источник называет значение; указать, какой.
- **Допущение** — источники молчат, разумное простое поведение; пользователь подтвердит.
- **Вопрос** — от ответа зависит модель данных или логика, любое допущение вероятно придётся переделать. Это **блокирующий** вопрос.

Допущение, которое оказалось дорогим, повышается до вопроса.

## 4. Вопросы

Каждое неизвестное — в `docs/open-questions.md` со следующим номером, в формате файла: вопрос → «Сейчас» (что будет в коде, пока не ответили) → «Решает» → «Добавлено». Блокирующий — пометка **«Блокирует <фича>»**. Что именно неясно, формулировать конкретно: значения из источников и где они расходятся, а не «как лучше?».

Пользователю — пачкой в разговоре, блокирующие первыми. Каждый вопрос с рекомендованным ответом («Сейчас»): пользователь отвечает «ок» или правит. Не спрашивать то, что показывает Figma или скриншот.

## 5. Карточка готовности

В flow doc фичи (`projects/<flow>/<name>.md`) раздел «Готовность» — до решений и кода. Обновляется после каждого ответа, пока не исчезнет «Блокирует».

```markdown
## Готовность

Проверено: <дата>. Статус: **готова** / **готова с допущениями** / **заблокирована** (#N, #M).

| Область | Статус | Источник / чего не хватает |
|---|---|---|
| Назначение | есть | спецификация, «Назначение» |
| Данные | вопрос | #30: типы пассажира |
| … | … | … |

**Материалы:** спецификация (`sources/…`), Figma `<file key>` · `<node id>`, скриншоты 4, запись 22 с.
**Не получено:** <что просили и не дали, чем заменено>.
```

Статус карточки: **заблокирована**, пока есть блокирующий вопрос; **готова с допущениями** — вопросов нет, допущения не подтверждены; **готова** — всё подтверждено пользователем.

## 6. После ответов

- В `docs/open-questions.md`: под вопросом «**Решено <дата> (пользователь):** …». Номера не перенумеровывать.
- Во flow doc: решения — раздел «Решено» (таблица № → решение), подтверждённые допущения — «Допущения» с датой. Ответ пользователя — правило продукта (правило 9).
- Статус карточки обновить; запись в таблице виджетов `projects/booking-overview/README.md` (или в flow doc другой фичи).
- Дальше — `create-screen` или `build-component`; для виджета Booking Overview — карточка готовности «готова» или «с допущениями» (не «заблокирована»).

## Чего не делать

- Не писать код, пока карточка «заблокирована».
- Не задавать вопросов, на которые уже отвечают источники.
- Не класть в репозиторий скриншоты и записи с реальными данными.
- Не закрывать вопрос своим допущением: допущение подтверждает пользователь.
